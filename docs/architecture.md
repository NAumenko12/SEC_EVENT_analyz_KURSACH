# Архитектура

Security Event Analyzer состоит из десктопного клиента на React и Tauri, C++ API
на Drogon, PostgreSQL, Apache Kafka и отдельного C++ worker. Компоненты разделены
так, чтобы при обработке большого файла интерфейс не зависал, а HTTP-сервер
продолжал отвечать на запросы пользователя.

Пользователь начинает работу в отдельном окне десктопного приложения. React
формирует интерфейс, а Tauri упаковывает его в нативное приложение. Tauri не
заменяет серверную часть: клиент по-прежнему отправляет HTTP-запросы в Drogon
API. Поэтому получение справочников выполняется через `GET`, загрузка файла —
через `POST`, а состояние анализа можно периодически получать отдельным
`GET`-запросом.

На первом этапе клиент и API запускаются на одном компьютере. Такое разделение
всё равно полезно: интерфейс не получает пароль от PostgreSQL и не зависит от
реализации анализа. В дальнейшем API, PostgreSQL, Kafka и worker можно перенести
на сервер, а в desktop-клиенте изменить только адрес API.

Получив файл, API проверяет его тип и размер, сохраняет в выделенное хранилище,
добавляет записи в `uploads` и `analysis_jobs`, а затем публикует сообщение в
Kafka. В сообщении находятся идентификаторы загрузки и задачи, но не содержимое
самого файла.

Kafka выступает границей между быстрым HTTP-запросом и длительным анализом.
Сообщения публикуются в topic `analysis.jobs`. API работает как producer, а
worker входит в consumer group `security-analyzer-workers`. Если позднее будет
запущено несколько worker, Kafka сможет распределять задачи между ними.

Получив сообщение, worker читает сведения о задаче из PostgreSQL, выбирает
подходящий парсер и обрабатывает файл. Полученные записи приводятся к общей
модели событий и сохраняются в `events` вместе с таблицами подробностей для HTTP,
Suricata, DNS и сетевых пакетов. После нормализации worker применяет правила
обнаружения, создаёт findings и формирует итоговый отчёт.

PostgreSQL является основным постоянным хранилищем системы. В нём находятся
пользователи, сведения о загруженных файлах, состояние задач, события, правила,
результаты обнаружения и отчёты. Kafka хранит только сообщения, необходимые для
асинхронной доставки задач, и не заменяет базу данных.

В локальной среде Kafka запускается одним узлом в режиме KRaft и совмещает роли
broker и controller. Этого достаточно для разработки и демонстрации курсовой.
Промышленное развёртывание потребовало бы нескольких брокеров, отдельных
настроек безопасности, репликации и мониторинга, но оно не входит в границы
учебной версии.

Первый вертикальный сценарий системы будет готов, когда API сможет получить из
PostgreSQL список типов источников, а десктопный клиент покажет их пользователю.
Серверная половина этого сценария уже реализована в `GET /api/source-types`.
Следующим шагом десктопный клиент вызовет этот endpoint и выведет полученный
список. После этого появятся загрузка файлов, публикация задач в Kafka, обработка
worker и отображение результатов анализа.
