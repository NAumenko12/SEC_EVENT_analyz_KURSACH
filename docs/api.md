# HTTP API

API реализовано на C++ с помощью Drogon и по умолчанию доступно по адресу
`http://127.0.0.1:8080/api`.

## Проверка состояния

`GET /api/health` возвращает имя сервиса и состояние API.

## Регистрация и вход

`POST /api/auth/register` принимает JSON с полями `username`, `email` и
`password`. Имя содержит от 3 до 32 латинских букв, цифр или символов `_.-`, а
пароль — от 15 до 128 символов. При успехе API создаёт пользователя и возвращает
`201 Created`:

```json
{
  "token": "случайный bearer-токен",
  "user": {
    "id": 7,
    "username": "analyst",
    "email": "analyst@example.com",
    "role": "user"
  }
}
```

`POST /api/auth/login` принимает `login` и `password`. В поле `login` можно
передать имя пользователя или email. Ответ имеет такую же структуру.

`GET /api/auth/me` возвращает текущего пользователя, а
`POST /api/auth/logout` отзывает текущую сессию и отвечает `204 No Content`.
Для этих и остальных защищённых запросов токен передаётся так:

```text
Authorization: Bearer <token>
```

Отсутствующий, истёкший или отозванный токен возвращает `401 Unauthorized`.

## Типы источников

`GET /api/source-types` читает из PostgreSQL список поддерживаемых источников.
Desktop-клиент использует его для построения карточек выбора.

## Загрузка файла

`POST /api/uploads` принимает `multipart/form-data` с двумя полями:

- `source_type` — код из справочника `source_types`;
- `file` — один журнал или сетевой дамп размером до 20 МБ.

Запрос требует bearer-токен. Идентификатор владельца берётся только из
проверенной сессии и не принимается из формы.

API проверяет расширение и базовую сигнатуру содержимого, заменяет исходное имя
случайным UUID, вычисляет SHA-256 и сохраняет файл в `data/uploads`. После этого
одна SQL-команда создаёт строки в `uploads` и `analysis_jobs`. Затем API
публикует идентификаторы задания и загрузки в Kafka topic `analysis.jobs`.

Успешный ответ имеет статус `201 Created`:

```json
{
  "uploadId": 12,
  "jobId": 8,
  "status": "queued"
}
```

Некорректный файл возвращает `400 Bad Request`. Внутренняя ошибка хранения или
базы возвращает `500 Internal Server Error` без раскрытия деталей клиенту.

## Состояние задания

`GET /api/jobs/{id}` возвращает актуальное состояние анализа:

```json
{
  "id": 8,
  "uploadId": 12,
  "status": "completed",
  "progress": 100,
  "processedRecords": 245,
  "eventsCreated": 0,
  "findingsCreated": 0,
  "errorMessage": null
}
```

Неизвестный или принадлежащий другому пользователю идентификатор возвращает
`404 Not Found`. Desktop-клиент опрашивает этот endpoint, пока задание не
получит конечный статус.
